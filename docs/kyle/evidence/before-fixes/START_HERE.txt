## 1. Read before running

Open [App.jsx](../../frontend/src/App.jsx) beside [STATIC_TESTING.md](STATIC_TESTING.md).

Start with `completeQuest` at line 53. Follow this sequence on paper:

1. No profile? Return without writing anything.
2. Matching completion record? Alert and return.
3. Compute the new XP and level.
4. Update the profile in the database.
5. If that update fails, return.
6. Insert the quest-completion record.
7. If that insert fails, return.
8. Update React's local state and show a success alert.

The key review question is: **At step 7, what happened to the data saved at step 4?** It was already saved. This is why ST-01 exists. A successful first write and failed second write can leave inconsistent data.

Next read lines 58-62 and 119-125. These use matching IDs to identify completions. Ask: **Where does the code check whether `completed` is true?** It does not. The subsequent [read-only schema review](SCHEMA_REVIEW.md) confirmed that the real completed column defaults to false, supporting this test input.

## 2. Run automated static analysis

Use Node 24.22.3 (the verified version) or another version allowed by `frontend/package.json`. A supported Node installation normally supplies npm. Open a terminal in the project's frontend folder:

```sh
npm ci
npm run lint
```

`npm ci` installs exactly the locked dependencies. `npm run lint` runs ESLint. An exit code of 0 with no diagnostics is the recorded baseline result. ESLint does not execute the dashboard and does not establish whether the two database writes are atomic.

The assistant environment used `pnpm dlx npm@11.19.1` in place of `npm` because npm was not on PATH. You do not need that wrapper when npm works normally on your machine.

## 3. Understand the test tools

- **Vitest** discovers cases, executes them, and checks assertions.
- **React Testing Library** renders the real React component and finds its visible output.
- **jsdom** supplies a simulated document; no browser window opens.
- **The Supabase mock** supplies known rows and controlled errors without contacting a backend.
- **V8 coverage** records which source statements, branches, and functions executed.

The setup follows the official [Vitest configuration](https://vitest.dev/config/), [coverage](https://vitest.dev/guide/coverage.html), [module mocking](https://vitest.dev/guide/mocking/modules), and [React Testing Library setup](https://testing-library.com/docs/react-testing-library/setup/) documentation.

## 4. Read one test slowly

Open [App.test.jsx](../../frontend/src/App.test.jsx) and find WB-02.

Each case follows **Arrange -> Act -> Assert**:

1. Arrange: build known test data, such as an empty transaction list.
2. Act: render App and wait until its loading effect completes.
3. Assert: check that the dashboard displays the expected balance, percentages, and counts.

WB-04 supplies two income records totaling $1,050 and two expense records totaling $250. The expected net balance is $800. The rounded savings rate is 76%. The test checks these values as constants, rather than calculating them with App's own formula, so it can catch an incorrect implementation.

This is white-box design because we read the filter/reduce/map operations and selected zero, one, and several records to exercise those paths. An assertion about visible text can still be part of a white-box test.

Run only this case:

```sh
npm test -- -t "WB-04"
```

Then run the ordinary baseline cases:

```sh
npm run test:baseline
```

The verified result is 28 passing cases. This command omits the two defect cases on purpose; it is useful for learning and does not represent the full result.

## 5. Read the red tests

Open [App.defects.test.jsx](../../frontend/src/App.defects.test.jsx), then run:

```sh
npm run test:defects
```

The full run is:

```sh
npm test
```

The original App currently produces **28 passed, 2 failed, 0 skipped**. The failures are genuine assertions, not skipped tests or tests configured to pass when they fail.

- CQ-D001 expects stored XP to remain 90 after the completion insert fails; the simulated service actually stores 100. The screen still shows 90. This is the partial-write finding from your source review.
- CQ-D002 expects an incomplete record to leave the quest available; the rendered component instead puts it in Completed Quests. The real schema's false default was subsequently confirmed; live integration reproduction remains pending.

Exit code 1 is expected while these defects/proposed requirements remain unresolved. Do not change the expected XP to 100 just to make the suite green. First agree on the intended behavior, make a justified correction, and rerun the case. If the schema proves a state unsupported, document the evidence and reclassify the case openly.

## 6. Read coverage with the failures in view

```sh
npm run test:coverage
```

The report is written even though the two cases fail. Open [the HTML coverage report](evidence/coverage/index.html) and click App.jsx. Its baseline coverage is 96.73% statements and 92.18% branches. The whole-source totals are lower because the browser bootstrap and real service initialization are not exercised.

Coverage answers **which code ran**, while assertions answer **whether the observed behavior met expectations**. This project demonstrates the difference: high coverage and two failed checks can coexist.
