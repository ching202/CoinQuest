## Approach and environment

The tests import and render the real `App.jsx`. React state and effects execute normally in a jsdom document. Only the Supabase module is replaced with a controlled service. The test cases were selected from the source's statements, decisions, early returns, and array-processing paths, so they support white-box testing even though most assertions inspect rendered output.

Verified environment: Windows, Node 24.22.3, npm 11.19.1, Vitest 5.1.1, V8 coverage 5.1.1, React Testing Library 16.3.3, and jsdom 31.0.1. The exact versions are locked in `frontend/package-lock.json`. npm was invoked using `pnpm dlx npm@11.19.1` in the assistant environment because standalone npm was absent from PATH. On a normal compatible Node/npm installation, use the npm commands below directly.

The fixture adapter supports the App's read/order/update/filter/insert operations. It honors update equality filters, keeps simulated persisted state separate from React state, and returns inserted rows from insert().select(). It does not model database constraints, access policies, RPCs, transactions, retries, or concurrent users. Unexpected fetch calls throw. No Supabase URL or key is needed for these tests.

## Commands

From `frontend/`, with Node 24.22.3 recommended:

```sh
npm ci
npm run lint
npm run test:baseline
npm test
npm run test:coverage
npm run build
```

- `test:baseline`: the 28 currently passing component cases; this is a subset, not final acceptance.
- `test`: all 30 cases, including two failing defect reproductions. It currently returns exit code 1.
- `test:defects`: just the two defect cases, for investigation.
- `test:coverage`: all cases plus coverage, including a report when tests fail.
- `test:watch`: reruns tests while files are edited; stop it with Ctrl+C.

The baseline and defect subset scripts write their own JSON files. The full run writes `test-results.json`. Rerunning a command replaces its generated evidence, so preserve an original failure snapshot before recording a correction.

## Statement, branch, and loop evidence

- **Statements:** loading data, computing totals, updating a profile, inserting a completion, and rendering sections execute in the suite. Instrumented statement coverage is reported below.
- **Branches:** positive/zero income, financial-health thresholds, profile-present/absent, read success/error, write success/error, achievement locked/unlocked, and quest empty/nonempty paths are exercised.
- **Loops:** App.jsx has no explicit for/while loop. Its filter/reduce/map/some callbacks perform collection iteration. WB-02, WB-03, and WB-04 exercise zero, one, and multiple transaction records; WB-07 uses two profiles to cover both map outcomes. Coverage tools do not supply a separate loop-coverage percentage, so this input design is documented explicitly.

Generated by the full 30-case run, including the two failures:

| Scope | Statements | Branches | Functions | Lines |

| App.jsx | 96.73% (89/92) | 92.18% (59/64) | 96.00% (24/25) | 96.29% (78/81) |
| All included application source | 92.70% (89/96) | 86.76% (59/68) | 96.00% (24/25) | 91.76% (78/85) |

The whole-source denominator includes `main.jsx` and `supabase.js`; these are not exercised because App is mounted directly and the real service module is mocked. Tests and test helpers are excluded from the coverage denominator.

Remaining App gaps include the duplicate-check callback and already-completed early return (lines 60, 65-66), the empty insert-response fallback (line 111), and the no-profile completion-filter fallback (line 121). A completed quest's button is removed from the rendered interface, so the ordinary user flow does not reach every defensive duplicate-check path. Rapid repeated clicks/concurrency and a testable completion service deserve follow-up; these are not claimed covered.

No arbitrary coverage threshold was added: the assignment requires a report but specifies no percentage. High coverage does not close the two failed defect checks.
